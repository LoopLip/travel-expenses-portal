# Портал командировок и расходов

Учебный full-stack проект по курсу «Fullstack» (1 семестр). Сотрудники оформляют командировки, запрашивают авансы и отчитываются о расходах; руководитель согласует заявки, бухгалтер выдаёт авансы; руководитель и бухгалтер ведут бюджеты отделов.

Все пять лабораторных выполнены, итог — работающий MVP: интерфейс на React работает с API на FastAPI, данные хранятся в PostgreSQL. По теме проекта сумма и дата расхода **распознаются с фотографии чека** (Tesseract OCR и правила разбора текста), а человек проверяет подставленные значения перед сохранением — раздел [«Распознавание чека»](#распознавание-чека).

| Лабораторная | Тема | Тег |
|---|---|---|
| №1 | Интерфейс приложения и каркас frontend | `lab-1` |
| №2 | Backend, API и работа с базой данных | `lab-2` |
| №3 | Архитектура frontend и динамический интерфейс | `lab-3` |
| №4 | Аутентификация и авторизация | `lab-4` |
| №5 | Интеграция frontend и backend | `lab-5` |
| №5 + тема проекта | Распознавание суммы и даты по фото чека | `lab-5-ocr` |

Структура репозитория: `frontend/` (React + TypeScript), `backend/` (FastAPI), `docker-compose.yml` (PostgreSQL), `docs/` (скриншоты, [карта интеграции](docs/integration-map.md)).

## Запуск с нуля (Windows, PowerShell)

Нужны: **Git**, **Docker Desktop**, **Python 3.11+**, **Node.js 20+** и (для e2e и скриншотов) Google Chrome. Команды выполняются из PowerShell; пути указаны от корня репозитория.

### 1. Код и база данных

```powershell
git clone https://github.com/LoopLip/travel-expenses-portal.git
cd travel-expenses-portal
Copy-Item .env.example .env
notepad .env                      # задайте POSTGRES_PASSWORD (любой пароль для локальной БД)
docker compose up -d              # PostgreSQL 16 на порту 5433
docker compose ps                 # STATUS: Up ... (healthy)
```

### Адреса и порты

| Что | Адрес |
|---|---|
| Интерфейс | <http://localhost:5173> |
| API и Swagger | <http://localhost:8000>, <http://localhost:8000/docs> |
| PostgreSQL | `localhost:5433` (порт 5433, чтобы не конфликтовать с локальным PostgreSQL на 5432; меняется `POSTGRES_PORT` и `DATABASE_URL`) |

**Один хост для страницы и API.** Refresh-токен лежит в cookie, а `localhost` и `127.0.0.1` браузер считает разными сайтами. Если открыть страницу на `localhost`, а API указать на `127.0.0.1` (или наоборот), cookie не отправится и после F5 придётся входить заново. Поэтому `VITE_API_URL` по умолчанию пустой: frontend обращается к API на том же хосте, что и страница, порт 8000. `CORS_ORIGINS` backend по умолчанию разрешает оба варианта адреса frontend.

## Роли и что кому доступно

Права проверяет **backend** (`backend/app/permissions.py` и роутеры). Интерфейс повторяет те же правила в одном месте (`frontend/src/entities/session/model/permissions.ts`), чтобы скрывать недоступные кнопки; если сервер всё же отказал, показывается «Недостаточно прав…».

| Операция | Сотрудник | Руководитель | Бухгалтер |
|---|---|---|---|
| Видеть командировки, авансы, расходы | только свои (чужое — 404) | все | все |
| Создать командировку | на себя | на любого сотрудника | нет |
| Изменить, удалить командировку | свою | любую | нет |
| Сменить статус командировки | своей: только «Черновик» и «На согласовании» | любой | нет |
| Запросить аванс, изменить сумму, удалить аванс | по своим командировкам | да | да |
| Сменить статус аванса (выдан, закрыт) | нет | нет | да |
| Добавить, изменить, удалить расход | по своим командировкам | да | нет (только просмотр) |
| Бюджеты: просмотр и использование | да | да | да |
| Бюджеты: создание, изменение, удаление | нет | да | да |
| Страница «Сотрудники» | нет (403) | да | да |

Чужая запись для сотрудника «не существует» (404), а не «запрещена» (403): так нельзя по id выяснить, есть ли запись.

## Как устроена интеграция (ЛР №5)

Подробная таблица «экран → действие → эндпоинт → роль» и все найденные несовпадения форматов — в [docs/integration-map.md](docs/integration-map.md).

```mermaid
flowchart LR
    P[pages: страница] --> F[features: действие / форма]
    F --> E["entities/*/api: tripApi, expenseApi…"]
    E --> M["mappers.ts: Zod-проверка ответа,<br/>форма → тело запроса"]
    E --> H["shared/api/httpClient:<br/>токен, refresh при 401, ошибки"]
    H -->|fetch + Authorization: Bearer| B[FastAPI: routers → permissions → crud]
    B --> D[(PostgreSQL)]
    E -->|после POST/PATCH/DELETE| BUS[шина notifyDataChanged]
    BUS -->|повторная загрузка| Q[useQuery на открытых экранах]
```

- **Запросы.** Каждая сущность (`trip`, `advance`, `expense`, `budget`, пользователи в `session`) имеет `api/*Api.ts` с реальными запросами через общий `httpClient` (access-токен в заголовке, одно обновление по refresh-cookie при 401, повтор запроса).
- **Мапперы** (`entities/*/api/mappers.ts`) — единственное место преобразования форматов. Ответ сервера проверяется схемой Zod: суммы приводятся к виду `"0.00"`, даты — `YYYY-MM-DD`, статусы — допустимые значения. Значения форм превращаются в тело запроса (обрезка пробелов, `"72000,5"` → `"72000.50"`, id числами). Имена полей совпадают с API (`snake_case`): типы frontend с ЛР №3 описаны по схемам backend, переименование ничего бы не дало.
- **Обновление после изменений.** Изменяющие запросы идут через `mutate()`, которая после успеха вызывает `notifyDataChanged()`. Все открытые `useQuery` загружают данные заново: список, карточка, суммы командировки и использование бюджета обновляются без перезагрузки страницы. Прежние данные остаются на экране до прихода новых.
- **Отмена устаревших запросов.** `useQuery` передаёт в запрос `AbortSignal`: при смене фильтра или уходе со страницы прежний запрос отменяется и не перезапишет новый ответ.
- **Фильтры на сервере.** Статус и поиск командировок, статус авансов, категория и поиск расходов уходят параметрами запроса (`?status=&q=`). Поиск отправляется через 300 мс после окончания ввода.
- **Ошибки.** 422 переводится на русский и показывается у полей формы; 400 и 409 — текстом сервера; 403 — «Недостаточно прав…» без кнопки «Повторить»; 404 — «Запись не найдена» (карточка — страница 404); нет ответа — «Нет связи с сервером» и «Повторить». Кнопки отправки и удаления блокируются на время запроса.

## Распознавание чека

Сотрудник прикладывает фото чека в форме расхода — сервер распознаёт текст, находит сумму и дату и предлагает их в поля формы. **Человек всегда проверяет результат**: расход сохраняется только кнопкой «Сохранить», подставленные значения подписаны «Подставлено из чека. Проверьте».

### Как это работает

```mermaid
flowchart LR
    A[ExpenseForm / ReceiptUpload<br/>проверка типа и размера, миниатюра] -->|POST /receipts/recognize<br/>multipart, токен| B[routers/receipts.py<br/>роль: С или Р]
    B --> C[receipt_ocr.py<br/>Pillow: формат, лимиты,<br/>поворот, серый, контраст, увеличение]
    C --> D[Tesseract OCR<br/>rus+eng]
    D --> E[receipt_parser.py<br/>сумма и дата по правилам]
    C --> F[(backend/uploads/receipts/&lt;uuid&gt;.png)]
    E -->|amount, expense_date, receipt_url| A
    A -->|человек проверил → POST /expenses c receipt_url| G[(PostgreSQL)]
```

1. **Tesseract** — свободная программа распознавания текста на изображении (в версиях 4+ символы распознаёт небольшая нейросеть LSTM). Она работает локально, без интернета и без ключей.
2. **Подготовка изображения** (`receipt_ocr.py`): реальный формат проверяется по содержимому файла (JPEG, PNG, WEBP), а не по имени. Есть лимиты: размер файла (`MAX_RECEIPT_MB`) и число пикселей (защита от «бомб» распаковки). Затем изображение поворачивается по EXIF (фото с телефона), переводится в оттенки серого, контраст выравнивается, мелкие картинки увеличиваются.
3. **Правила разбора** (`receipt_parser.py`) — обычные функции без OCR, полностью покрытые тестами:
   - **сумма** — число рядом с «ИТОГО», «К ОПЛАТЕ», «TOTAL», «ВСЕГО», «СУММА» (строки с НДС, сдачей, скидкой пропускаются), иначе наибольшая сумма с копейками. Поддерживаются форматы «1 234,50», «1234.50», «1234-50», «1234,5». Типичные ошибки OCR внутри чисел исправляются: О→0, l/I→1, S→5;
   - **дата** — форматы «ДД.ММ.ГГГГ», «ДД.ММ.ГГ», «ДД/ММ/ГГГГ», «ГГГГ-ММ-ДД», «12 окт 2026», «12 октября 2026». Будущие даты и даты старше ~5 лет отбрасываются; приоритет у даты рядом со словами «ДАТА» и «ЧЕК», иначе берётся самая поздняя.
4. **Файл** сохраняется как `backend/uploads/receipts/<uuid>.<ext>`: имя файла от пользователя не используется. Распознанный текст не возвращается и не пишется в лог. Расход сервер **не создаёт** — это только предложение для формы.
5. **«Открыть чек»** — `GET /expenses/{id}/receipt` отдаёт файл только тем, кто видит расход (чужой для сотрудника — 404). Отдаются только ссылки вида `receipts/<uuid>.(jpg|jpeg|png|webp)`; старые записи с условными именами получают 404 «Файл чека недоступен».

Ответы: 401 — нет входа, 403 — бухгалтер (расходы только просматривает), 413 — файл больше лимита, 415 — не JPEG/PNG/WEBP, 422 — файл не является изображением, 503 — Tesseract недоступен. «Ничего не нашли» — **не ошибка**: 200 и `recognized: false`, форма просит ввести данные вручную.

### Установка Tesseract на Windows (с русским языком)

1. Скачайте установщик **UB Mannheim**: <https://github.com/UB-Mannheim/tesseract/wiki> (64-bit).
2. В установщике откройте **Additional language data (download)** и отметьте **Russian** (английский ставится по умолчанию).
3. Проверьте в новом окне PowerShell:
   ```powershell
   tesseract --version
   tesseract --list-langs      # в списке должны быть rus и eng
   ```
4. Если команда `tesseract` не найдена, укажите путь в `backend/.env`:
   ```
   TESSERACT_CMD=C:\Program Files\Tesseract-OCR\tesseract.exe
   ```
5. Перезапустите backend. `GET /receipts/status` (или кнопка «Загрузить фото чека» в форме расхода) покажет, что распознавание доступно.

**Без Tesseract** приложение работает как раньше: кнопка загрузки фото отключена с подсказкой «Распознавание недоступно на сервере, введите данные вручную», расход вводится вручную. Тест с настоящим Tesseract пропускается, сквозной сценарий проверяет отключённую кнопку.

### Точность

### Ограничения

- Качество зависит от фото: нужен ровный, резкий снимок всего чека при хорошем освещении. Рукописные и сильно повреждённые чеки не распознаются.
- Правила рассчитаны на типичные российские кассовые чеки; нестандартная вёрстка (несколько итогов, итог словами) может дать неверную сумму — поэтому человек всегда проверяет значения.
- Распознаются только сумма и дата; категорию и описание человек вводит сам.
- Файлы хранятся в `backend/uploads` на диске сервера, автоматически не чистятся (в том числе после удаления расхода или если расход так и не сохранили). Миграций нет — поле `receipt_url` осталось прежним.

- Удаление командировки каскадно удаляет её авансы и расходы. Пользователя и бюджет с командировками удалить нельзя (`RESTRICT`, ответ 409).
- CHECK-ограничения в БД: суммы положительные (план — неотрицательный), `end_date >= start_date`. Статусы и категории хранятся строкой `VARCHAR(20)` **без** CHECK: допустимые значения проверяют перечисления Python и схемы Pydantic.
- Бизнес-правила: сумма авансов командировки не больше плановой суммы (400); плановую сумму нельзя снизить ниже авансов (400); резерв бюджета — плановые суммы поездок, кроме черновиков и отклонённых (`GET /budgets/{id}/summary`).

### API

Swagger: <http://localhost:8000/docs>. Все ресурсы, кроме `/auth/*` и `/health`, требуют access-токен.

| Ресурс | Операции и фильтры |
|---|---|
| `/auth` | `POST /register`, `POST /login` (форма OAuth2), `POST /refresh` (cookie), `POST /logout`, `GET /me` |
| `/users` | список (Р, Б), `GET/PATCH /{id}` (свой или Р, Б), `DELETE` (Р) |
| `/budgets` | CRUD (изменение — Р, Б), `GET /{id}/summary` — резерв и остаток |
| `/trips` | CRUD; фильтры `status`, `user_id`, `budget_id`, `q` (направление, цель, ФИО) |
| `/advances` | CRUD; фильтры `trip_id`, `status` |
| `/expenses` | CRUD; фильтры `trip_id`, `category`, `q` (описание); `GET /{id}/receipt` — файл чека (только тем, кто видит расход) |
| `/receipts` | `GET /status` — доступно ли распознавание; `POST /recognize` — фото чека (multipart, поле `file`) → сумма, дата, `receipt_url`; С и Р, бухгалтер — 403 |

Списки: `skip` (≥ 0) и `limit` (1…500, по умолчанию 100). Ошибки: `{"detail": "текст"}` для 400, 401, 403, 404, 409 и `{"detail": [{type, loc, msg, ctx}]}` для 422. Деньги в JSON — строки с двумя знаками (`"5000.50"`), даты — `YYYY-MM-DD`, `created_at` — UTC с `Z`.

## Аутентификация (ЛР №4)

- Пароли — только хеш **argon2id**. Ответ на неверный email и неверный пароль одинаковый.
- **Access-токен** — JWT (HS256), 15 минут, в заголовке `Authorization: Bearer`, хранится только в памяти страницы.
- **Refresh-токен** — 7 дней, в cookie `HttpOnly; SameSite=Lax; Path=/auth`; в БД — только SHA-256. При каждом обновлении выдаётся новый (ротация); повтор старого считается кражей и отзывает всю сессию.
- После F5 сессия восстанавливается запросом `/auth/refresh`. При нескольких одновременных 401 frontend делает один refresh, остальные запросы ждут его и повторяются.
- Выход отзывает сессию на сервере и очищает состояние на клиенте; после этого refresh-cookie не работает.

## Известные ограничения

- **Таблицы создаются через `create_all` без миграций**: существующие таблицы не изменяются. После изменения моделей БД пересоздаётся (`docker compose down -v`). Для данных, которые нужно сохранять, нужен Alembic.
- **Пагинации в интерфейсе нет**: списки запрашиваются с максимальным `limit=500`, записи сверх 500 не покажутся. Для реального объёма данных нужна постраничная загрузка.
- Использование бюджетов загружается отдельным запросом `GET /budgets/{id}/summary` на каждый бюджет (бюджетов в отделах немного).
- Данные не кешируются: после любой мутации открытые экраны перезагружают свои данные целиком. Это просто и надёжно, но даёт лишние запросы.
- Распознавание чека зависит от качества фото и формата чека: см. ограничения в разделе [«Распознавание чека»](#распознавание-чека). Файлы чеков хранятся в `backend/uploads` и не удаляются автоматически (в том числе после удаления расхода).
- Правил переходов между статусами нет (как и в backend): руководитель может поставить любой статус. Сотрудник может менять свою заявку в любом статусе — так решает backend.
- Нет смены пароля, восстановления доступа, подтверждения email, ограничения частоты запросов. Пользователи с ролью создаются только командой `create-user`/`seed-demo`; управления пользователями в интерфейсе нет.

## Что изменилось в ЛР №5 и почему

- **Демо-хранилище удалено.** Командировки, авансы, расходы и бюджеты читаются и пишутся в PostgreSQL через API. Удалены `localStorage`-коллекции, имитация сети и панель «Демо-режим» в меню: состояния загрузки и ошибки теперь возникают от реальных запросов.
- **Кнопки зависят от роли.** Бухгалтер не видит создания и изменения командировок и расходов, сотрудник — управления бюджетами и чужих данных, смена статуса командировки показывает только допустимые для роли статусы. Раньше интерфейс показывал всё, а права проверялись только на API.
- **Форма командировки.** Поле «Сотрудник» есть только у руководителя: сотрудник оформляет командировку на себя, бухгалтер не оформляет вовсе.
- **Фильтры уходят на сервер.** Поиск в расходах ищет по описанию (backend не ищет по направлению командировки); поиск командировок — по направлению, цели и ФИО.
- **Новые действия:** изменение расхода и суммы аванса, создание, изменение и удаление бюджетов — их требует пункт 2 методички (CRUD через интерфейс по правам роли).
- **Ошибки сервера у полей формы**, отдельные сообщения для 403, 404, 409 и отсутствия связи.
- **Использование бюджета** берётся из сводки сервера, а не считается на клиенте.

### Распознавание чека (после тега `lab-5`, тег `lab-5-ocr`)

- **Имитация заменена настоящим распознаванием.** Раньше после выбора файла подставлялись фиксированные значения, а файл никуда не загружался. Теперь фото уходит на сервер, распознаётся Tesseract, сумма и дата находятся правилами разбора, файл сохраняется и открывается кнопкой «Открыть чек».
- **В форме расхода** появились миниатюра чека, индикатор «Распознаём чек…» (кнопка «Сохранить» на это время заблокирована) и подписи у подставленных значений. Вручную исправленное поле новый чек не перезаписывает. Если Tesseract не установлен, кнопка загрузки отключена с подсказкой.
- **Подзаголовок страницы «Новый расход»** теперь говорит, что значения нужно проверить: раньше он обещал, что всё «подставится автоматически».

## Как запускалось и проверялось

- Backend: `pytest` — 159 тестов на реальном PostgreSQL (CRUD, валидация, права ролей, аутентификация, серверные фильтры, `seed-demo`, разбор текста чеков, загрузка чеков и коды ошибок) и 1 тест с настоящим Tesseract, который пропускается, если Tesseract с языком `rus` не установлен.
- Frontend: `tsc -b`, `oxlint`, `lint:layers`, `vitest` (71 тест: мапперы, деньги и даты, HTTP-клиент, загрузка файла и ответ-файл, перевод ошибок 422, ошибки в формах, проверка файла чека, подстановка распознанных значений, правила форм, охрана маршрутов), `vite build`.
- `npm run e2e` — 34 шага в Chrome на реальном backend (шаг с распознаванием чека выполняется, если на сервере есть Tesseract, иначе пропускается и проверяется отключённая кнопка загрузки): регистрация → вход → создание командировки → она в списке и после F5 → редактирование → аванс → расход (добавление, изменение, удаление) → отправка на согласование → использование бюджета → выход; руководитель согласует заявку, ищет и фильтрует на сервере, создаёт командировку за сотрудника, управляет бюджетами (в т.ч. отказ 409); сотрудник не видит чужого (404) и получает «Доступ запрещён» (403); бухгалтер выдаёт аванс и не видит лишних кнопок; тихое обновление истёкшего access-токена; состояния загрузки, «нет связи», пусто; 404; мобильная ширина; `prefers-reduced-motion`; отсутствие ошибок в консоли.
- Инструкция «Запуск с нуля» пройдена буквально в чистом клоне репозитория с новой БД (`docker compose down -v`, затем `up -d`).
