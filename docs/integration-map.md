# Карта интеграции frontend ↔ backend (ЛР №5)

Документ составлен по коду backend (`backend/app/schemas.py`, `routers/*.py`, `permissions.py`, `crud.py`) и по реальным ответам запущенного API (запросы через Python `urllib` к `http://127.0.0.1:8000`, Swagger на `/docs`). Права ролей взяты **только** из backend. Интерфейс повторяет их для удобства (скрывает недоступные кнопки), но решение всегда принимает сервер.

Обозначения ролей: **С** — сотрудник (`employee`), **Р** — руководитель (`manager`), **Б** — бухгалтер (`accountant`).
«Свои» — записи командировок, где `trip.user_id` = id текущего пользователя. Чужую запись сотрудник не видит: сервер отвечает **404**, а не 403, чтобы не раскрывать, что запись существует (`permissions.py`).

## 1. Экран → действие → эндпоинт → кто может

| Экран | Действие | Эндпоинт backend | Кто может (по backend) |
|---|---|---|---|
| Вход `/login` | Войти | `POST /auth/login` (форма `username`, `password`) | все |
| Регистрация `/register` | Зарегистрироваться (роль всегда С) | `POST /auth/register`, затем `POST /auth/login` | все |
| Любой | Восстановить сессию после F5 | `POST /auth/refresh` (cookie), `GET /auth/me` | все с действующим refresh |
| Меню пользователя | Выйти | `POST /auth/logout` | все |
| Обзор `/` | Сводка | `GET /trips`, `GET /advances`, `GET /expenses`, `GET /budgets`, `GET /budgets/{id}/summary` | С (только свои), Р, Б (все) |
| Командировки `/trips` | Список с фильтром по статусу и поиском | `GET /trips?status=&q=&limit=500` | С — свои; Р, Б — все |
| Командировки `/trips` | Имена сотрудников в списке | `GET /users?limit=500` | Р, Б (С видит только свои поездки, имя берётся из сессии) |
| Командировки `/trips` | Удалить | `DELETE /trips/{id}` | С (свои), Р |
| Новая заявка `/trips/new` | Создать | `POST /trips` (`user_id` можно не передавать — оформляется на себя) | С (только на себя), Р (на любого) |
| Новая заявка | Списки для формы | `GET /budgets`, `GET /users` (только Р) | все / Р, Б |
| Редактирование `/trips/:id/edit` | Изменить поля | `GET /trips/{id}`, `PATCH /trips/{id}` | С (свои), Р |
| Карточка `/trips/:id` | Просмотр с авансами и расходами | `GET /trips/{id}` (ответ `TripDetail` уже содержит `advances` и `expenses`), `GET /budgets/{id}`, `GET /users/{id}` | С (свои), Р, Б |
| Карточка | Сменить статус | `PATCH /trips/{id}` `{status}` | Р — любой статус; С — только `draft` и `pending` у своих; Б — нет |
| Карточка / Авансы `/advances` | Запросить аванс | `POST /advances` | С (свои поездки), Р, Б |
| Карточка / Авансы | Изменить сумму аванса | `PATCH /advances/{id}` `{amount}` | С (свои), Р, Б |
| Карточка / Авансы | Сменить статус аванса | `PATCH /advances/{id}` `{status}` | только Б |
| Карточка / Авансы | Удалить аванс | `DELETE /advances/{id}` | С (свои), Р, Б |
| Авансы `/advances` | Список с фильтром по статусу | `GET /advances?status=&limit=500` | С — свои; Р, Б — все |
| Карточка / Расходы `/expenses` | Добавить расход | `POST /expenses` | С (свои поездки), Р; Б — нет |
| Карточка / Расходы | Изменить расход | `PATCH /expenses/{id}` | С (свои), Р; Б — нет |
| Карточка / Расходы | Удалить расход | `DELETE /expenses/{id}` | С (свои), Р; Б — нет |
| Расходы `/expenses` | Список с фильтром по категории и поиском | `GET /expenses?category=&q=&limit=500` | С — свои; Р, Б — все |
| Бюджеты `/budgets` | Просмотр с использованием | `GET /budgets`, `GET /budgets/{id}/summary` | все вошедшие |
| Бюджеты | Создать / изменить / удалить | `POST /budgets`, `PATCH /budgets/{id}`, `DELETE /budgets/{id}` | Р, Б |
| Сотрудники `/users` | Список | `GET /users?limit=500` | Р, Б; С — 403 |

Удаление командировки на сервере каскадно удаляет её авансы и расходы (`ON DELETE CASCADE`). Удаление бюджета, к которому привязаны командировки, запрещено (409).

## 2. Несовпадения форматов и как они решены

### Имена полей и вложенность
- Backend отдаёт поля в `snake_case` (`planned_amount`, `start_date`, `user_id`). Типы frontend уже были описаны в `snake_case` (ЛР №3 строилась по схемам backend), поэтому имена полей **не переименовываются**: это убирает лишний слой ошибок при сопоставлении. Решение записано в README.
- `GET /trips/{id}` возвращает **вложенные** массивы `advances` и `expenses` (`TripDetail`), а `GET /trips` — плоский `TripOut` без них. В демо-версии карточка собирала авансы и расходы фильтрацией общих списков; теперь берёт их из ответа карточки.
- В ответах командировок нет имени сотрудника и названия бюджета — только `user_id` и `budget_id`. Имена подставляются из `GET /users` (Р, Б) или из сессии (С), бюджет — из `GET /budgets`.
- `UserOut` содержит `role`; демо-тип `User` его не имел. Тип пользователя объединён с `SessionUser`.
- Входящие ответы проверяются Zod-схемами в мапперах (`entities/*/api/mappers.ts`); при несовпадении показывается «Некорректный ответ сервера», а не падение страницы.

### Статусы и перечисления
| Поле | Значения backend | Подписи на экране |
|---|---|---|
| `trip.status` | `draft`, `pending`, `approved`, `rejected`, `completed` | Черновик, На согласовании, Согласована, Отклонена, Завершена |
| `advance.status` | `requested`, `issued`, `settled` | Запрошен, Выдан, Закрыт отчётом |
| `expense.category` | `transport`, `lodging`, `meals`, `other` | Транспорт, Проживание, Питание, Прочее |
| `user.role` | `employee`, `manager`, `accountant` | Сотрудник, Руководитель, Бухгалтер |

Значения совпадают; подписи хранятся только во frontend (`entities/*/model/labels.ts`). Недопустимое значение в запросе backend отклоняет с 422 (тип `enum`). В БД ограничения CHECK на эти столбцы нет (обычный `VARCHAR(20)`), допустимые значения проверяют перечисления Python и схемы Pydantic.

### Деньги
- Backend хранит `Numeric(12, 2)` и в JSON отдаёт `Decimal` **строкой**: `"5000.50"`, `"600000.00"`.
- Найдено несовпадение: `GET /budgets/{id}/summary` при отсутствии резерва отдавал `"reserved": "0"` (без копеек), а не `"0.00"`. Исправлено в backend (значение приводится к двум знакам), добавлен тест.
- Frontend считает деньги в копейках (`shared/lib/money.ts`), чтобы не терять точность на `number`; на экран выводит через `Intl.NumberFormat('ru-RU', RUB)`; на сервер отправляет строку с точкой и двумя знаками (`"72000,5"` → `"72000.50"`, функция `normalizeMoney`). Маппер ответа нормализует все суммы к виду `"0.00"`.
- Ошибки сервера о суммах (`decimal_max_places`, `greater_than`) переводятся на русский и показываются у поля.

### Даты и время
- Даты (`start_date`, `end_date`, `expense_date`, `requested_at`) — строка `YYYY-MM-DD` без часового пояса.
- `created_at` — момент времени в UTC с суффиксом `Z` (`2026-11-01T11:28:40.616260Z`).
- Несовпадение: прежний `formatDate` разбирал `YYYY-MM-DD` через `new Date(iso)`, что трактуется как полночь UTC; в часовых поясах западнее UTC дата сдвигалась на день назад. Теперь дата без времени разбирается как локальная календарная дата, а `created_at` — как момент UTC и показывается в местном времени.
- `requested_at` у аванса ставит сервер (`current_date()` PostgreSQL) — клиент его не отправляет.

### Списки и фильтры
- Все списки: `skip` (≥ 0, по умолчанию 0) и `limit` (1…500, по умолчанию 100). `limit=501` → 422.
- Пагинации в интерфейсе нет, поэтому frontend запрашивает `limit=500` (максимум) и честно указывает это ограничение в README.
- Фильтры backend до ЛР5: `GET /trips?status=&user_id=&budget_id=`, `GET /advances?trip_id=`, `GET /expenses?trip_id=`. В интерфейсе были ещё поиск по командировкам, фильтр авансов по статусу, фильтр и поиск расходов — они выполнялись на клиенте. Чтобы фильтры уходили на сервер, в backend добавлены параметры `GET /trips?q=` (направление, цель, ФИО сотрудника), `GET /advances?status=`, `GET /expenses?category=&q=` (описание), с тестами.
- Для сотрудника параметр `user_id` в `GET /trips` игнорируется: он всегда видит только свои записи.

### Формат ошибок
| Код | Тело | Когда | Как показывает интерфейс |
|---|---|---|---|
| 401 | `{"detail": "строка"}` + `WWW-Authenticate: Bearer` | нет/истёк access-токен, неверный пароль | тихое обновление по refresh-cookie и повтор запроса; если не удалось — переход на вход с сообщением «Сессия истекла» |
| 403 | `{"detail": "Недостаточно прав для этого действия"}` | роль не может выполнить операцию | «Недостаточно прав…» (кнопка «Повторить» не показывается) |
| 404 | `{"detail": "Командировка с id=1 не найден(а)"}` | записи нет или она чужая (для С) | «Запись не найдена», для карточки — страница 404 |
| 400 | `{"detail": "строка"}` | нарушено бизнес-правило (лимит авансов, план меньше авансов, даты) | текст сервера под формой или в уведомлении |
| 409 | `{"detail": "строка"}` | конфликт (email занят, бюджет с командировками, пользователь с командировками) | текст сервера |
| 422 | `{"detail": [{"type", "loc", "msg", "input", "ctx"}]}` | ошибка валидации Pydantic (сообщения на английском) | список переводится на русский по `type`/`ctx`; ошибка с `loc: ["body", "<поле>"]` выводится у поля формы, ошибка всей модели (`loc: ["body"]`, например «дата окончания не может быть раньше даты начала») — под формой |
| сеть | — | backend не запущен, CORS, обрыв | «Нет связи с сервером» и кнопка «Повторить» |

### CORS и cookie
- `CORS_ORIGINS` по умолчанию разрешает `http://localhost:5173` и `http://127.0.0.1:5173`, `allow_credentials=True`, методы `GET, POST, PATCH, DELETE, OPTIONS`, заголовки `Authorization, Content-Type` (проверено preflight-запросом `OPTIONS /trips`).
- Refresh-токен — HttpOnly-cookie с `SameSite=Lax` и `Path=/auth`. `localhost` и `127.0.0.1` браузер считает **разными сайтами**: если страница открыта на одном хосте, а API указан на другом, cookie не отправится и после F5 сессия не восстановится. Поэтому `VITE_API_URL` по умолчанию не задаётся, и frontend обращается к API на том же хосте, что и страница (порт 8000).
